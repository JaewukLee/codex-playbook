# 팀별 업무 프로필

여기서 프리셋은 **업무 성격의 정의**이며 구성원 명단이 아니다. 팀 이름만으로 특정 에이전트나 모델을 자동 배정하지 않는다.

## 업무 유형

| 이름 | 별칭 | 목적·업무 성격 | 필요한 관점 | 주요 산출물 |
| --- | --- | --- | --- | --- |
| 요구사항 협의 | discovery | 초안을 목표와 범위로 구체화 | 사용자 흐름, 우선순위, 단순성 | 수용 기준, 포함·제외 범위, 미결 질문 |
| 기술 설계 | design | 구현 가능한 구조와 계약 결정 | 책임 경계, 대안, 실패·복구 | 설계 결정, 계약, 변경 영향 |
| 태스크 계획 | planning | 실행 가능한 단위로 분해 | 의존 관계, 수정 소유권, 검증 가능성 | 태스크 목록, 순서, 완료 조건 |
| 버그 수정 | bugfix | 원인 해결과 기존 동작 보존 | 재현, 원인 분석, 회귀 | 최소 수정, 재현·정상 경로 검증 |
| 신규 기능 | feature | 합의한 사용자 동작 구현 | 사용자 가치, 구현, 실패 흐름 | 기능, 수용 기준별 검증 |
| 외부 API 연동 | integration | 시스템 사이의 계약 연결 | 스키마, 권한, 재시도, 부분 실패 | 연결 구현, 성공·실패 검증 |
| 구조 리팩터링 | refactor | 외부 동작을 보존하며 구조 개선 | 책임, 가독성, 호환성 | 구조 변경, 동작 보존 증거 |
| 성능 개선 | performance | 측정된 병목 개선 | 대표 부하, 측정, 정확성 | 전후 수치, 절충, 회귀 결과 |
| 전체 인수 확인 | acceptance | 태스크 결과가 전체 목표를 충족하는지 확인 | 사용자 흐름, 통합, 회귀 | 요구사항별 판정과 미검증 범위 |

관점은 필요한 역량을 나타내며 에이전트 수를 의미하지 않는다. 한 명이 여러 관점을 맡을 수 있다. 독립 검증이 필요한지는 작업 위험과 검증 근거에 따라 팀 구성 시 정한다.

## 유형별 완료·인계 기준

- discovery: 원문·사실·가정을 구분하고, 범위와 수용 기준을 기록한다. 제품 선택의 미결 질문을 숨기지 않는다.
- design: 선택한 구조·대안 제외 이유·계약·실패 조건·검증 방식을 정한다. 이미 합의한 설계를 불필요하게 다시 만들지 않는다.
- planning: 태스크의 결과, 입력, 의존 관계, 수정 경계, 검증 방법을 명시한다. 순환 의존과 공유 파일 충돌을 해소한다.
- bugfix: 원인 근거와 수정된 재현 사례, 관련 정상 경로 검증을 제시한다.
- feature: 합의한 수용 기준과 성공·빈 상태·실패·복구 흐름의 결과를 제시한다.
- integration: 인증·오류·재시도 계약을 구현 전에 확인한다. 모의 검증과 실제 연동 검증을 구분한다.
- refactor: 보존할 외부 동작과 계약을 정하고 변경 후 증거를 제시한다. 동작 변경은 별도로 다룬다.
- performance: 같은 대표 조건의 기준·개선 수치·변동과 정확성 검증을 함께 제시한다. 미측정 개선을 단정하지 않는다.
- acceptance: 최종 변경 상태에서 사용자 흐름과 통합 결과를 확인한다. 결함은 실행 담당에게 돌려보내거나 후속 작업으로 분리한다.

## 구성 협의

1. [Mosaic](../agents/coordination/mosaic.toml) 역할로 업무 목표·범위·제약과 필요한 관점을 정리한다. 메인이 이 지침을 읽어 직접 대화할 수 있으며, 상담용 서브에이전트를 반드시 생성할 필요는 없다.
2. 역할 파일에서 후보를 비교하고 각 후보의 담당 범위와 선정 이유를 설명한다. 필요한 경우 기존 역할의 임시 업무 지침 또는 새 역할 후보를 제안한다. 기존 명단에 억지로 맞추지 않는다.
3. 최소 구성안을 우선 제안하고, 중요한 절충이 있으면 보강안 하나를 비교한다. 인원·모델·effort·협업 순서·검증 독립성·수정 소유권을 논의한다.
4. [팀 구성 기록](../templates/team-composition.md)에 사용자와 정한 구성을 남긴다. 사용자가 구성을 위임한 경우에는 위임 범위 안에서 정하고 그 근거를 기록한다. 이미 정한 내용을 반복해서 확인받지 않는다.
5. 구성 합의와 태스크 실행 지시는 구분한다. 실행 지시가 있으면 합의한 구성을 실행 담당에게 인계한다. 팀 이름만 지정된 경우에는 곧바로 고정 멤버를 생성하지 않는다.

## 공통 운영 조건

- 전체 프로세스는 [WORKFLOW.md](../WORKFLOW.md)를 따른다. 협의·설계·계획·인수 확인은 배정된 문서·분석·검증을 수행하며 제품 코드는 수정하지 않는다.
- 리드도 구성 협의에서 정한다. 메인이 실행 리드를 맡기로 한 경우 리드 에이전트를 중복 생성하지 않는다. 구성 상담은 실행 리드의 상시 관리 계층이 아니다.
- 각 역할의 입력·산출물·완료 조건·수정 경계와 실제 모델·effort를 배정한다. 업무 프로필에는 모델 기본값이나 멤버를 중복 저장하지 않는다.
- 실제 동시 실행 한도를 따른다. 의존 작업은 순차로 진행하고 같은 파일의 병렬 수정을 피한다.
- 검증에서 나온 범위 내 결함은 수정·재검증한다. 필수 검증이 남으면 Done으로 보고하지 않는다.
- 구성 변경이 필요하면 이유와 영향을 기록한다. 이미 위임된 조정 범위에서는 진행하고, 위임되지 않은 중요한 변경은 사용자와 의논한다.
- 완료 보고에는 업무 프로필, 실제 구성, 구성 변경 이유, 검증 근거를 남긴다.

## 재사용 요청

```text
agents/coordination/mosaic.toml을 읽고 팀 구성 상담을 해줘.
업무 성격은 bugfix이고, 대상은 …야.
범위와 필요한 역량부터 정리하고 후보 에이전트·모델·effort를 제안해줘.
이번에는 구성만 의논하고 실행하지 마.
```

```text
<팀 구성 기록>에 합의한 구성으로 <태스크>만 실행해줘.
업무 기준은 teams/TEAM_PROFILES.md의 integration을 따르고 결과를 기록해줘.
```
