# 역할 기반 에이전트 팀

구성·설계·구현·검증·조사·지식 관리 분야의 16개 역할 후보를 관리한다. 파일을 작성하는 것만으로 실행 중인 에이전트가 생성되지는 않는다. 태스크마다 필요한 역할을 선택한다.

전체 운영 흐름은 [요구사항 협의와 태스크 중심 실행](../WORKFLOW.md)을 따른다. 요구사항을 사용자와 논의한 뒤 태스크를 기록하고, 사용자가 지정한 태스크에 실행팀을 배정한다. 업무 프로필에는 멤버를 고정하지 않는다. Mosaic와 필요한 역량과 후보를 의논하고 실제 구성은 별도 기록으로 정한다.

## 원본 관리와 실행용 배치

역할 원본은 `agents/` 아래 분류별로 관리하며, 실행용 `.codex/agents/*.toml`은 수정하지 않는다. `coordination`, `design`, `implementation`, `verification`, `research`, `knowledge`는 파일 분류이며 고정 팀을 뜻하지 않는다. 팀 성격은 `teams/TEAM_PROFILES.md`, 실제 구성은 태스크의 팀 구성 기록에 둔다.

Python 3.11 이상에서 저장소 루트 기준으로 실행한다.

```bash
python3 scripts/deploy_agents.py
python3 scripts/deploy_agents.py --check
```

스크립트는 하위 폴더 원본을 읽어 평탄하게 배치한다. 이름·파일명 중복, 필수 필드와 TOML 문법을 검사한다. 관리 이력의 해시로 실행용 파일의 직접 수정 여부를 확인하며, 충돌이 있으면 파일을 변경하기 전에 중단한다. 직접 수정한 실행용 파일은 내용을 원본에 반영한 뒤 다시 배치한다.

삭제·이름 변경된 역할의 사본은 이전 배치가 관리했고 이후 수정되지 않은 경우에만 정리한다. 다른 도구나 사용자가 추가한 파일은 보존한다. 기존 사본은 원본과 내용이 같은 경우에만 관리 대상으로 채택한다. `.codex/agents/.deployment-manifest.json`은 배치 이력이므로 직접 편집하지 않는다. `--check`는 파일을 쓰지 않고 최신 여부와 충돌을 검사한다.

새 역할도 자동으로 실행되거나 팀에 편입되지는 않는다. Mosaic와 의논할 때 후보로 비교한다. 실제 모델 가용성과 실행은 별도로 확인한다.

## 모델과 추론 노력 기본값

2026-11-06에 지정한 초기값이다. 실제 성과를 측정한 최적값이 아니며 운용 결과에 따라 수정한다. 여러 조건의 변화를 구분하기 위해 Sol과 Luna 두 모델로 시작하고, 최고 effort를 모든 역할에 일괄 적용하지 않는다.

| 역할 | model | model_reasoning_effort | 초기 선택 이유 |
| --- | --- | --- | --- |
| mosaic | `gpt-6.1-sol` | `high` | 업무 제약·후보·검증 구조의 절충 비교 |
| compass | `gpt-6.1-sol` | `high` | 여러 판단과 결과를 통합 |
| atlas | `gpt-6.1-sol` | `high` | 모듈 경계와 변경 영향 분석 |
| occam | `gpt-6.1-sol` | `medium` | 대안을 비교해 복잡성 축소 |
| sentinel | `gpt-6.1-sol` | `high` | 실패·동시성·복구 설계 |
| bolt | `gpt-6-luna` | `high` | 범위가 명확한 작은 기능 구현 |
| scalpel | `gpt-6.1-sol` | `high` | 원인 분석과 호환성 보존 |
| weaver | `gpt-6.1-sol` | `medium` | 합의된 계약에 따른 통합 구현 |
| forge | `gpt-6.1-sol` | `medium` | 동작을 보존하는 구조 정돈 |
| pulse | `gpt-6.1-sol` | `high` | 측정 해석과 성능·정확성 절충 |
| probe | `gpt-6.1-sol` | `high` | 실패·권한·동시성 반례 탐색 |
| journey | `gpt-6-luna` | `high` | 명시적 수용 기준과 사용자 흐름 대조 |
| anchor | `gpt-6.1-sol` | `high` | 호출자·공개 계약의 회귀 분석 |
| scout | `gpt-6.1-sol` | `medium` | 실제 코드 경로와 증거 추적 |
| harness | `gpt-6.1-sol` | `high` | 결정적인 재현·테스트 환경 구축 |
| curator | `gpt-6.1-sol` | `medium` | 여러 회고의 근거 비교와 규칙 정리 |

설정의 기준은 각 역할 TOML의 최상위 `model`, `model_reasoning_effort` 필드다. 업무 프로필은 필요한 관점과 산출물을 정한다. 구성 협의에서 역할과 모델·effort를 정하고, 역할 파일의 기본값을 참고한다. 모델별 effort의 의미가 같다고 가정하지 않는다. Luna의 high와 Sol의 high가 같은 품질·비용·시간을 뜻하지는 않는다.

```toml
model = "gpt-6.1-sol"
model_reasoning_effort = "high"
```

### 실행 시 적용

- 커스텀 역할 설정을 지원하는 클라이언트에서는 역할 파일의 모델·effort를 적용한다. 지침 문자열만 읽어서 전달하는 방식에서는 리드가 두 설정도 실행 인자로 명시해야 한다.
- 현재 협업 도구는 전체 대화를 상속하는 생성 방식에서 모델·effort 변경을 지원하지 않는다. 역할별 설정을 적용할 때는 `fork_turns="none"`으로 생성하고 `model` 및 `reasoning_effort`를 전달한다. 역할의 전체 지침, 목표, 파일 경로, 관련 결정, 완료 조건을 함께 전달한다. 다른 실행 도구에서는 해당 도구의 지원 방식을 확인한다.
- 메인이 Compass를 맡으면 `compass.toml`의 설정을 읽어도 실행 중인 메인의 모델은 바뀌지 않는다. 리드는 현재 세션 모델로 동작한다는 점을 보고하고, 파일 설정은 별도로 생성하는 Compass 또는 이후 세션 구성의 기준으로 사용한다.
- 지정 모델을 사용할 수 없으면 성공적으로 적용했다고 보고하지 않는다. 제약과 대안을 알리고 사용자의 모델 선택 조건을 따른다.
- 작업 배정 시 요청한 모델·effort를 기록한다. 런타임에서 실제 설정을 확인할 수 있으면 함께 기록하고, 확인하지 못한 경우 요청값과 실측값을 구분한다.

### 운용 중 조정

Bolt·Journey는 범위와 수용 기준이 명확한 작업을 기준으로 Luna를 배정했다. 복잡한 원인 분석이나 모호한 판단에서 반복 실패하면 Sol로 변경하는 후보로 삼는다. 각 역할은 품질, 재작업, 시간, 제공되는 경우 토큰·비용을 같은 태스크 조건에서 비교한다. 모델과 effort를 한꺼번에 바꾸기보다 한 변수씩 조정한다.

사용자가 수정한 역할 파일을 다음 배정 전에 다시 읽는다. 한 태스크의 임시 변경은 배정에 기록하고 영구 기본값 변경과 구분한다. 기존 프리셋의 이름만 지정했다고 이 표의 모델이 실제 실행에 자동 적용되었다고 가정하지 않는다.

근거: [OpenAI 공식 서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents). 모델 및 effort의 지원 범위는 실행 환경에서도 확인해야 한다.

## 사용 방법

커스텀 에이전트를 지원하는 로컬 Codex 클라이언트의 프로젝트용 위치는 `.codex/agents/`, 개인용 위치는 `~/.codex/agents/`다. 역할 원본은 이 저장소의 `agents/<분류>/`에 있고 `.codex/agents/`는 배치된 실행용 사본이다. 실제 저장소를 별도의 프로젝트 루트로 열면 그 프로젝트의 `.codex/agents/`에 필요한 TOML을 배치한다. 같은 이름의 기존 파일은 비교 후 병합한다.

설정 탐색 범위와 등록 여부는 사용하는 클라이언트에서 확인해야 한다. 이 파일을 생성한 세션에서 역할이 자동으로 다시 로드되었다고 가정하지 않는다. 이름 기반 선택이 제공되지 않는 환경에서는 메인이 해당 TOML의 `developer_instructions`를 읽고 위임 지침으로 전달할 수 있다.

먼저 `agents/coordination/mosaic.toml`을 읽어 구성 상담을 요청한다. 메인이 상담 역할을 직접 맡을 수 있다.

> Mosaic 역할로 팀 구성을 의논해줘. 요구사항은 …이고 중요한 제약은 …야. 필요한 역량부터 정리하고 최소 구성안과 선정 이유를 제안해줘. 이번에는 구성만 정하자.

구성 합의 후에는 팀 구성 기록과 실행할 태스크를 전달한다. 기존에 실행까지 지시했다면 그 권한을 다시 확인받지 않는다.

## 팀 업무 프로필 재사용

[teams/TEAM_PROFILES.md](../teams/TEAM_PROFILES.md)에 협의·계획용 `discovery`, `design`, `planning`, 전체 인수용 `acceptance`와 태스크 실행용 `bugfix`, `feature`, `integration`, `refactor`, `performance`를 저장했다. 각 항목은 업무 성격을 정의한다. 멤버는 Mosaic와 의논해 [팀 구성 기록](../templates/team-composition.md)에 남기며 리드 역시 그 과정에서 정한다. 이는 에이전트가 읽는 운영 지침이며 별도 내장 명령은 아니다.

> Mosaic와 bugfix 업무를 위한 팀 구성을 의논해줘. 대상은 로그인 오류 메시지 누락이며, 재현 가능성과 변경 영향부터 확인해서 후보를 제안해줘.

새 대화에서는 문서 경로를 포함한다. 프로젝트를 옮길 때는 역할 TOML과 teams/TEAM_PROFILES.md를 함께 복사한다.

전체 프로세스까지 복사할 때는 playbook 루트의 WORKFLOW.md와 templates/도 포함하고 문서 링크를 확인한다. 또는 원본 playbook의 절대 경로를 작업 요청에 전달해 재사용한다.

현재 작성 세션의 동시 활동 한도는 메인 포함 4명이다. 이 숫자를 다른 환경의 영구 한도로 가정하지 말고 실행 시 제공되는 한도를 따른다. 설계·구현·검증은 의존 순서대로 진행하며, 독립적인 작업만 병렬화한다. 슬롯이 부족하면 기존 에이전트에 후속 작업을 배정하거나 사용 가능한 세션 종료 기능으로 슬롯을 확보한다. 완료 상태가 자동으로 슬롯을 해제한다고 가정하지 않는다.

## 업무 배정 양식

```text
역할:
목표:
입력 문서 / 코드 / 이전 결정:
수정 허용 파일 또는 읽기 전용 범위:
유지할 계약 / 다른 담당자와의 경계:
선행 조건:
완료 조건:
필요한 검증:
보고 형식:
```

## 인계와 완료

- 같은 파일은 동시에 여러 구현 담당에게 배정하지 않는다. 공유 계약 변경은 리드가 조율한다.
- 설계 인계에는 추천안, 대안 제외 이유, 변경 대상, 검증 기준을 담는다.
- 구현 인계에는 변경 파일, 실제 동작, 실행한 검증, 남은 제약을 담는다.
- 검증 인계에는 발견 위치, 발생 조건, 영향, 재현 또는 코드 근거, 미검증 범위를 담는다.
- 리드는 최종 변경 상태를 검증하고 완료 조건별 결과를 보고한다. 중요한 결정은 프로젝트의 기존 문서 위치에 남긴다.
- 모든 역할의 이전 작업 기억이 다음 세션에 자동으로 유지된다고 가정하지 않는다.

## 운영 노하우와 지침 관리

작업에서 얻은 노하우는 적용 범위에 맞는 파일에 저장한다. 역할의 성향, 팀의 작업 방식, 프로젝트 제약, 개별 작업의 관찰 기록을 구분하면 필요한 맥락만 전달할 수 있다.

### 적용 범위와 저장 위치

| 적용 범위 | 저장 위치 | 예시 |
| --- | --- | --- |
| 개별 에이전트 | `agents/<분류>/<역할>.toml` 원본의 `developer_instructions` | Scalpel은 공통 함수 수정 전에 호출자를 확인한다. |
| 특정 팀 | [teams/TEAM_PROFILES.md](../teams/TEAM_PROFILES.md)의 해당 프리셋 | integration 팀은 구현 전에 오류 응답 계약을 확정한다. |
| 프로젝트 전체 | 해당 프로젝트의 `AGENTS.md` | 생성된 코드는 직접 수정하지 않는다. |
| 이번 태스크만 | 사용자 요청 또는 리드의 업무 배정 | 이번 작업은 설계까지만 진행한다. |
| 작업 회고와 근거 | 프로젝트의 기존 회고·결정 기록 위치 | 발생한 문제, 대응, 결과, 재사용할 교훈을 기록한다. |

회고 위치가 없다면 프로젝트 안에 `docs/agent-team/retrospectives/` 같은 경로를 정해 사용할 수 있다. 이는 제안하는 문서 구조이며 자동으로 생성되거나 읽히는 경로가 아니다. 리드의 작업 입력에 관련 기록 경로를 포함한다.

### 개별 에이전트 속성 추가

“더 신중하게” 같은 추상적인 성격보다 관찰 가능한 행동을 적는다. 임의의 TOML 설정 키를 추가하는 대신 기존 `developer_instructions` 문자열 안에 지침을 넣는다.

```text
Scalpel 추가 규칙:
- 공통 함수를 수정하기 전에 모든 호출자를 확인한다.
- 수정 범위가 공개 API까지 확장되면 Compass에게 영향을 보고한다.
- 버그 수정에 무관한 리팩터링을 섞지 않는다.
```

여러 역할에 공통으로 적용할 프로젝트 규칙은 해당 프로젝트의 `AGENTS.md`에 두고, 역할 파일에는 역할 고유의 판단 기준을 남긴다. 같은 규칙을 여러 곳에 복사하면 변경 시 불일치가 생길 수 있으므로 공통 규칙을 바꿀 때는 기존 중복 지침도 확인한다.

### 팀별 조언과 제한

프리셋 안에서 필수 규칙, 권장 사항, 적용 조건, 예외를 구분한다. 다음은 integration 팀에 추가할 수 있는 예시다.

```text
필수:
- 오류·재시도 계약이 정리된 뒤 구현한다. 담당자는 팀 구성 협의에서 정한다.
- 실제 API를 호출하지 못했으면 모의 검증만 수행했다고 보고한다.

권장:
- 외부 API 스키마가 불안정하면 작은 계약 검증부터 수행한다.

적용 조건:
- 외부 서비스와 통신하는 기능을 변경할 때.

예외:
- 동작이나 계약에 영향이 없는 문서 수정에는 연동 검증을 요구하지 않는다.
```

지침으로 둔 수정 제한은 행동 규칙이다. 파일 접근 자체를 차단해야 한다면 별도의 실행 권한 설정이 필요하다. 역할이나 팀 지침으로 실행 환경의 권한을 확대할 수는 없다.

### 노하우를 축적하는 절차

1. **회고 기록:** 작업 종료 후 문제, 원인, 효과가 있었던 대응, 결과와 근거를 남긴다.
2. **교훈 추출:** 일회성 상황과 재사용 가능한 교훈을 구분하고 적용할 역할·팀·프로젝트를 정한다.
3. **지침 반영:** 적용 조건, 필요한 행동, 예외를 명시한다. 기존 규칙과 중복·충돌하는지 확인한다.
4. **전달:** 다음 업무 배정 때 변경된 지침을 다시 읽는다. 진행 중인 에이전트에게는 리드가 변경 사항과 영향을 전달한다.
5. **정리:** 주기적으로 효과와 부작용을 검토하고 중복되거나 더 이상 맞지 않는 규칙은 통합·수정·제거한다.

한 번 발생한 문제를 모든 작업의 영구 제약으로 일반화하지 않는다. 예를 들어 공통 함수 수정 후 다른 호출 경로가 깨졌다면, 재현 근거를 기록하고 Scalpel의 호출자 확인 규칙과 Anchor의 호출자별 회귀 검증 규칙으로 나누어 반영할 수 있다.

회고 양식:

```text
날짜 / 태스크 / 사용한 프리셋:
참여 역할:
발생한 문제와 영향:
확인된 원인 / 아직 확인하지 못한 가설:
시도한 대응과 결과:
근거: 관련 코드, 테스트 결과, 결정 기록
재사용할 교훈:
적용 대상: 역할 / 팀 / 프로젝트
적용 조건과 예외:
제안하는 지침 변경:
상태: 제안 / 반영 / 보류 / 폐기
반영한 파일과 변경 이유:
재검토할 조건:
```

### 반영 권한과 적용 시점

추천 운영 방식은 회고를 작업마다 기록하고 지속적인 행동 변경은 제안 후 반영하는 것이다. 사용자가 “규칙에 반영해줘”라고 요청하거나 자동 개선 범위를 미리 지정했다면 그 범위에서 반영하며 같은 허락을 반복해서 요청하지 않는다. 이 절은 운영 방법 안내이며, README 작성만으로 자동 회고나 지침 변경 작업이 실행되는 것은 아니다.

자동 반영 범위는 다음처럼 명시할 수 있다.

> 매 작업 종료 시 회고를 기록해줘. 근거가 있는 프로젝트 내부 검증 절차는 자동 개선하되, 권한·작업 범위·팀 구성 변경은 먼저 제안해줘.

역할 파일 수정만으로 이미 실행 중인 에이전트의 지침이 갱신되었다고 가정하지 않는다. 리드가 변경 내용을 전달하고, 수정 범위나 완료 조건이 달라졌다면 기존 업무 배정과 충돌하지 않도록 조율한다. 새 작업에서는 최신 역할 파일과 관련 프리셋을 읽도록 요청한다.

### 재사용 요청 예시

개별 역할 개선:

> 이번 작업에서 얻은 교훈을 기록하고 Scalpel의 공통 함수 수정 규칙에 반영해줘. 적용 조건과 예외도 명시해줘.

팀 운영 개선:

> bugfix 프리셋에 “수정된 재현 사례와 관련 정상 경로를 함께 검증한다”는 필수 규칙을 반영해줘. 기존 규칙과 중복되면 통합해줘.

변경 전 검토:

> 최근 회고를 읽고 역할과 팀 프리셋의 개선안을 제안해줘. 이번에는 지침 파일을 수정하지 마.

규칙 정리:

> 역할 파일과 teams/TEAM_PROFILES.md에서 중복되거나 충돌하는 규칙을 확인해줘. 기존 의도를 보존하는 정리안을 제안해줘.
