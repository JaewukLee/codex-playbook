# 태스크별 팀 프리셋

이 문서는 Compass가 읽어 적용하는 팀 운영 지침이다. Codex의 내장 명령이나 자동 실행 설정이 아니다. 사용자가 프리셋을 지정하면 메인이 `compass.toml`의 리드를 맡고, 필요한 역할 파일을 읽어 서브에이전트에 지침을 전달한다. 역할 파일 경로는 이 문서가 있는 디렉터리를 기준으로 한다.

## 프리셋 목록

모든 팀의 리드는 Compass다. 화살표는 선행 단계의 결과를 받은 뒤 진행한다는 뜻이다.

| 이름 | 별칭 | 리드 외 구성 | 진행 순서 |
| --- | --- | --- | --- |
| 버그 수정 | bugfix | Scalpel, Anchor | 원인 분석·수정 → 회귀 검증 |
| 신규 기능 | feature | Occam, Bolt, Journey | 최소 설계 → 구현 → 사용자 흐름 검증 |
| 외부 API 연동 | integration | Sentinel, Weaver, Probe | 실패·계약 설계 → 연동 구현 → 반례 검증 |
| 구조 리팩터링 | refactor | Atlas, Forge, Anchor | 책임·경계 설계 → 구조 변경 → 동작 보존 검증 |
| 성능 개선 | performance | Pulse, Probe, Anchor | 기준 측정·개선 → 반례 및 회귀 검증 |

## 프리셋별 인계 기준

### 버그 수정 / bugfix

- Scalpel: 재현 조건, 기대·실제 동작, 원인 근거를 확인하고 최소 수정한다.
- Anchor: 수정된 재현 사례와 관련 정상 경로, 기존 계약을 확인한다.
- 완료 기준: 요청된 결함이 해결되고 관련 회귀 검증 결과가 제시되어야 한다. 재현이나 검증이 불가능하면 미확인으로 명시한다.

### 신규 기능 / feature

- Occam: 요구사항을 수용 기준으로 정리하고 기존 구조를 활용하는 최소 변경안을 제시한다.
- Bolt: 합의한 설계와 수용 기준에 맞춰 구현하고 필요한 구현 검증을 수행한다.
- Journey: 요구사항별 성공·빈 상태·실패·복구 흐름을 확인한다.
- 완료 기준: 수용 기준별 관찰 가능한 결과와 검증 근거를 제시한다.

### 외부 API 연동 / integration

- Sentinel: 요청·응답 계약, 인증, 타임아웃, 부분 실패, 재시도와 중복 처리 방침을 정한다.
- Weaver: 합의된 계약으로 구성 요소를 연결하고 성공·실패 경로를 구현한다.
- Probe: 잘못된 응답, 권한 경계, 중복·시간 초과 등의 주요 반례를 검증한다.
- 완료 기준: 핵심 성공·실패 흐름의 근거를 제시하고 모의 검증과 실제 연동 검증을 구분한다.

### 구조 리팩터링 / refactor

- Atlas: 현재 책임과 의존 관계, 보존할 계약, 점진적 변경 순서를 정한다.
- Forge: 배정된 범위에서 구조를 개선하고 관찰 가능한 동작을 보존한다.
- Anchor: 호출자 영향, 기존 계약과 회귀, 필요한 배포 호환성을 확인한다.
- 완료 기준: 구조 개선 근거와 동작 보존 검증을 제시한다. 동작 변경은 리드와 별도로 합의한다.

### 성능 개선 / performance

- Pulse: 대표 조건에서 기준을 측정하고 병목을 확인한 뒤 동일 조건으로 개선 전후를 비교한다.
- Probe: 개선으로 생길 수 있는 정확성·동시성·경계값 문제를 확인한다.
- Anchor: 기존 기능과 계약의 회귀 여부를 확인한다.
- 완료 기준: 측정 조건·수치·변동과 기능 검증 결과를 함께 제시한다. 성능 목표는 태스크에서 정하며, 측정 불가 시 개선을 단정하지 않는다.
- Probe와 Anchor는 구현이 안정된 뒤 독립적으로 검증할 수 있다. 공유 테스트 자원에 충돌이 있으면 순차 진행한다.

## 공통 운영 규칙

1. 사용자가 지정한 프리셋과 역할 변경 요청을 우선한다. 프리셋 선택을 맡겼다면 태스크의 주된 완료 조건을 기준으로 하나를 고르고 선택 이유를 알린다.
2. 필요한 역할의 TOML을 읽는다. 메인이 리드를 맡으며 Compass 서브에이전트를 추가로 만들지 않는다.
3. 사용자 목표·제외 범위·완료 조건을 확인하고 역할별 입력, 수정 허용 파일, 유지할 계약, 산출물을 배정한다.
4. 실제 런타임 한도 내에서 실행한다. 팀 구성원 전원을 동시에 실행할 필요는 없다. 의존 단계는 순차로, 독립 작업만 병렬로 진행한다.
5. 같은 파일의 수정 담당을 중복 배정하지 않는다. 검증 담당은 기본적으로 제품 코드를 수정하지 않는다.
6. 검증에서 결함이 발견되면 구현 담당에게 돌려보낸다. 수정 후 관련 검증을 다시 수행하고 최종 상태를 확인한다.
7. 추가 전문성이 필요하면 이유와 조정된 구성을 알리고 승인된 태스크 범위 안에서 역할을 보강한다. 사용자가 인원·역할·단계에 명시적 제한을 두었다면 그 제한을 따른다.
8. 최종 보고에 사용한 프리셋, 참여 역할, 주요 결정, 변경 결과, 검증 증거와 미확인 항목을 포함한다. 검증 불가를 통과로 간주하지 않는다.

## 재사용 요청 예시

```text
.codex/agents/TEAM_PRESETS.md의 bugfix 프리셋으로
서브에이전트 팀을 구성해줘. 네가 Compass 역할을 맡아줘.
태스크: 로그인 실패 시 오류 메시지가 표시되지 않는 버그 수정.
완료 조건: 실패 원인이 표시되고 정상 로그인은 유지된다.
```

```text
.codex/agents/TEAM_PRESETS.md에서 적합한 프리셋을 골라
서브에이전트 팀으로 진행해줘. 네가 Compass 역할을 맡아줘.
태스크: 사용자 알림 설정 기능 구현.
완료 조건: 알림을 켜고 끌 수 있고 다음 로그인에도 설정이 유지된다.
```

이 문서 경로를 이미 알고 있는 대화에서는 “bugfix 프리셋으로 이 버그를 수정해줘”처럼 줄여 요청할 수 있다. 새 대화에서는 파일 경로와 태스크를 함께 전달한다.
