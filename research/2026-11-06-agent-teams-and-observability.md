# 에이전트 팀 구성과 관측·효율 개선 사례

조사일: 2026-11-06. 영문 원문을 직접 확인한 자료를 한국어로 요약했다. 운영 조직의 기술 글, 해당 조직이 참여한 공급사 사례, 공식 연동 문서를 구분했다. 성과 수치는 작성자 측 보고이며 독립적인 재현 결과가 아니다. 개발 실험과 고객 지원 서비스의 결과를 같은 기준으로 비교하지 않는다.

## 1. Anthropic Research: 리드와 독립적인 조사 담당

- 구분·발행일: 제작사 기술 회고, 2025-06-13.
- 구성: 리드가 질문을 분해하고 하위 조사 담당들이 독립적으로 탐색한 뒤 결과를 반환한다. 인용 확인도 별도 역할로 둔다.
- 운영 방식: 목표, 출력 형식, 사용할 도구, 작업 경계를 명시한다. 질문 복잡도에 맞춰 에이전트 수와 탐색량을 제한한다.
- 효율 개선: 도구를 시험하는 에이전트로 도구 설명을 개선한 결과 후속 작업 시간이 40% 감소했다고 보고했다.
- 한계: 멀티에이전트는 해당 관측에서 일반 채팅 대비 약 15배의 토큰을 사용했다. 단일 에이전트 대비 15배라는 의미가 아니다. 의존성이 많은 코딩에는 병렬화의 이점이 줄어든다고 설명한다.
- 적용 아이디어: Compass의 배정 양식에 탐색 종료 조건과 도구 호출 예산을 추가하는 실험.

출처: [How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)

## 2. Cursor: 계획·구현·판정 분리

- 구분·발행일: 제작사 장기 코딩 실험, 2026-01-14.
- 구성: Planner가 작업을 만들고 Worker가 수행한다. Judge는 반복을 계속할지 판단한다.
- 관찰: 동등한 에이전트들이 공유 파일과 잠금으로 자율 조율하는 방식에서 대기와 책임 회피가 발생했다. 역할 분리 후 조율 문제가 완화되었다고 보고한다.
- 반례: 별도의 통합 담당을 추가했지만 병목이 되어 제거했다. 역할을 더 세분화하는 것이 항상 유리하지는 않았다.
- 한계: 대규모 실험이며 생성 코드량 자체가 품질이나 생산성의 증명은 아니다.
- 적용 아이디어: Compass가 모든 파일 편집을 직접 처리하지 않도록 하고, 설계 결정과 최종 완료 판단에 집중한다.

출처: [Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)

## 3. Anthropic C compiler: 테스트와 작업 격리 중심

- 구분·발행일: 연구 프로토타입, 2026-02-05.
- 구성: 16개 에이전트, 에이전트별 Docker 컨테이너와 로컬 clone, 공용 Git 저장소. 중앙 리드 없이 작업 잠금 파일로 중복 작업을 줄였다.
- 도구 활용: 테스트 하네스, CI, 진행 문서, 파일 로그를 이용해 다음 작업과 회귀를 판단했다.
- 효율 개선: 터미널에는 짧은 요약을 출력하고 상세 로그는 파일에 저장했다. 빠른 테스트 표본으로 피드백 시간을 줄였다.
- 한계: 약 2,000개 세션과 2만 달러 API 비용을 사용한 실험이다. 소규모 팀에 그대로 복제할 구성은 아니다.
- 적용 아이디어: 병렬 구현 시 작업 공간을 격리하고, 빠른 검사와 최종 통합 검사를 구분한다.

출처: [Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/research/building-c-compiler)

## 4. Lyft: 전문 에이전트 라우팅과 운영 대시보드

- 구분·발행일: Lyft 엔지니어 기고, LangChain 게시, 2026-05-27.
- 구성: 요청을 분류하는 라우터와 분야별 하위 그래프. 복잡한 전문 에이전트와 프롬프트·설정으로 정의하는 에이전트를 구분한다.
- 외부 도구: LangGraph로 실행 흐름, DynamoDB로 상태, LangSmith로 단계별 추적·평가, PagerDuty로 경보를 관리한다.
- 관측 항목: 오류율, p50/p95 지연, 토큰, 도구 성공률, 평가 추세. 단계별 입력·출력과 에이전트 식별 정보를 연결한다.
- 보고 성과: 개발 기간이 대략 6개월에서 몇 주로 줄었다. 전체 플랫폼·프로세스 개선의 결과이며 관측 도구만의 효과는 아니다.
- 적용 아이디어: 팀·역할·태스크 ID를 기록하고 실패 유형별로 분류한다.

출처: [How Lyft Built a Self-Serve AI Agent Platform](https://www.langchain.com/blog/lyft-built-a-self-serve-ai-agent-platform-for-customer-support-with-langgraph-and-langsmith)

## 5. ServiceNow: 실행 중간 상태를 보고 재시도

- 구분·발행일: ServiceNow와 LangChain 공동 사례, 2025-11-17. 글은 개발 중인 시스템으로 설명한다.
- 구성: Supervisor가 영업·온보딩·활용·갱신 등 분야별 담당을 조율한다. 작은 하위 그래프를 조합한다.
- 외부 도구: LangGraph, LangSmith, 지식 그래프와 MCP.
- 효율 개선: 전체 작업을 처음부터 재실행하는 대신 중간 상태를 확인하고 특정 단계에 다른 입력을 넣어 실험한다. 단계별 지연·토큰·컨텍스트를 추적한다.
- 한계: 공개 글에 비교 가능한 정량 생산성 개선치는 없다.
- 적용 아이디어: 설계 결과와 구현 결과를 명시적 산출물로 남겨 실패한 단계부터 재개할 수 있게 한다.

출처: [How ServiceNow uses LangSmith to get visibility into its customer success agents](https://www.langchain.com/blog/customers-servicenow)

## 6. Cresta: 서비스 경계를 넘는 실행 추적

- 구분·발행일: 고객 참여 Langfuse 사례, 2026-03-26. 다중 서비스 에이전트 파이프라인 사례이며 개발자 역할 팀과는 다르다.
- 외부 도구: 자체 호스팅 Langfuse와 gRPC 메타데이터를 통한 trace context 전파.
- 운영 방식: Go·Python 서비스의 검색·생성·도구 실행을 공통 trace/span ID로 연결한다. 최종 응답 오류의 원인이 어느 중간 단계에서 시작됐는지 찾는다.
- 효율 개선: 실패 지점의 프롬프트를 바꾸어 재실험한다. 토큰과 검색 결과 수 등으로 문제가 되는 실행을 필터링한다.
- 한계: 배포된 기능과 향후 탐색 중인 평가·프롬프트 회귀 감지 기능을 구분해야 한다.
- 적용 아이디어: 하나의 태스크 아래 리드·하위 에이전트·도구·검증 기록을 연결한다.

출처: [How Cresta traces multi-service AI agent pipelines with Langfuse](https://langfuse.com/users/cresta)

## 7. Slite: 회고 에이전트와 평가 데이터셋

- 구분·발행일: 고객 인터뷰 기반 Langfuse 사례, 2026-08-24. 지식 관리 에이전트의 개선 운영 사례다.
- 외부 도구: 자체 호스팅 Langfuse, 평가 데이터셋, CI, API 기반 회고 에이전트.
- 운영 방식: 약 100개 사례에 정답 문장 대신 기대 행동을 기록해 변경마다 평가한다. 회고 에이전트는 운영 trace를 표본 검토하고 개발자는 요약을 검토한다.
- 보고 성과: 분기 단위에서 주 단위 실험으로 전환해 약 12배의 실험 빈도를 보고했다. 12배 속도나 비용 절감이라는 뜻은 아니다.
- 한계: LLM 평가를 절대적인 merge 차단 조건이 아닌 품질·비용·지연 비교 신호로 사용한다.
- 적용 아이디어: 역할 지침 수정 전후에 같은 대표 태스크를 실행하고 회고를 규칙 개선의 근거로 삼는다.

출처: [How Slite Evaluates Its AI Agents with Langfuse](https://langfuse.com/users/slite)

## 8. Langfuse 코딩 에이전트 연동: 도구 후보

- 구분: 공급사의 공식 연동 안내. 도입 성과를 검증한 사례는 아니다.
- 기능: 코딩 세션의 모델·도구 실행, 토큰 사용, 실패 흐름을 추적한다. 에이전트별로 hook, 플러그인, OpenTelemetry 등 연동 방식이 다르다.
- 적용 아이디어: 현재 코딩 환경에 연결 가능한지 작은 샘플 실행으로 확인한 후 팀별 실행 비교에 사용한다.
- 확인할 것: 설치 버전, 현재 런타임의 이벤트 노출 범위, 하위 에이전트 연결 정보, 토큰 집계 완전성, 기록할 데이터 범위. 이번 조사에서는 설치하거나 연결을 시험하지 않았다.

출처: [Tracing coding agents with Langfuse](https://langfuse.com/resources/engineering/coding-agent-tracing)

## 사례 비교에서 얻은 판단

아래는 원문들의 주장 자체가 아니라 이 저장소에 적용하기 위한 제안이다.

1. **12개 역할은 선택 목록으로 유지한다.** 태스크마다 전원 투입하지 않는다. 작업이 분리되는 정도에 맞춰 팀을 구성한다.
2. **팀의 성격보다 작업 계약을 측정한다.** 목표, 수정 파일, 입력, 산출물, 검증 조건, 재시도 종료 조건을 명시한다.
3. **잠금이나 중앙 조율을 만능 해법으로 보지 않는다.** Anthropic 실험에서 사용한 잠금은 Cursor 실험에서는 병목이었다. 코드 소유권과 공유 자원의 특성에 맞춰 선택한다.
4. **관측과 제어를 구분한다.** 대시보드는 반복 호출을 보여줄 수 있지만 예산·시간·재시도 제한은 실행 계층이나 리드 지침에서 별도로 시행해야 한다.
5. **역할 개선을 실험으로 취급한다.** 실패 사례를 기록하고 지침 한 부분을 수정한 다음 동일 태스크로 비교한다. 과거 평가셋에만 맞추지 않도록 별도 확인 사례를 남긴다.

## 현재 팀에 권하는 적용 순서

### 1단계: Git과 실행 요약부터

태스크별로 다음 정보를 기록한다. 역할과 프리셋은 Git 커밋으로 버전을 식별한다. 제공되지 않는 토큰·비용은 추정으로 채우지 말고 미수집으로 표시한다.

```text
run_id / task_id / preset / role / parent_run_id
role_revision / target_commit
started_at / finished_at / status
tool_failures / retry_count / verification_result
tokens_if_available / cost_if_available
artifact_paths / failure_category / lesson
```

시작할 지표는 완료율, 첫 검증 통과율, 재작업 횟수, 완료 시간, 도구 실패 횟수다. 작업 난도가 다른 태스크의 원시 시간을 직접 비교하지 않는다.

### 2단계: 대표 평가 사례

bugfix·feature·integration 등 자주 쓰는 프리셋에 대표 태스크를 선정한다. 동일한 코드 시작 상태와 완료 조건으로 비교하고 코드 테스트를 우선한다. 사용자 흐름이나 설명 품질에만 보조 평가자를 활용한다. 단일 실행 결과만으로 역할 성향을 바꾸지 않는다.

### 3단계: 관측 도구 실험

코딩 세션 추적이 우선이면 Langfuse 연동의 적합성을 확인한다. 별도의 API 기반 워크플로를 개발한다면 LangGraph·LangSmith 조합도 후보가 된다. 현재 TOML·Markdown 팀이 이들 프레임워크로 자동 변환되는 것은 아니다. 우선 한 프리셋에서 추적 누락과 비용 집계를 확인한다.

### 4단계: 회고 자동화

실행 기록을 표본으로 모아 반복 실패를 요약하고, 관련 역할·프리셋의 변경안을 제안하게 한다. 자동 반영 범위는 기존 사용자 지침을 따른다. 외부 추적 저장소에는 필요한 정보만 보내고, 이 공개 Git 저장소에는 대화·코드 원문 대신 정제된 교훈과 평가 기준을 남긴다.
